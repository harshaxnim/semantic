Many cheap minds, many lenses:
a harness for decomposing hard problems

Finite elements break a continuum into small solvable cells. A Taylor series turns a hard function into a sum of easy terms. We want the same move for reasoning: look at a problem through many decomposition lenses, solve the small pieces with cheap models, check each piece locally, and compose the results back into an answer. The work is organized by a swarm that builds and explores a shared graph of constraints and partial solutions.

The thesis in four claims

Each claim can be proven wrong on its own, and the benchmark suite is built to test each one separately.

C1 · COMPOUNDING

Long chains fail because errors compound

A single model reasoning n steps at per-step reliability p succeeds about pn of the time. That curve falls off a cliff, which is what the "LLMs can't plan" and "illusion of thinking" results show as problems get harder.

C2 · LOCALITY

Small pieces can be checked locally

When a problem is cut into pieces with explicit interfaces (pre-conditions, post-conditions, constraints), each piece can be verified on its own and retried. Errors stop spreading through the chain, so depth costs far less.

C3 · DIVERSITY

No single decomposition works for every problem

Divide-and-conquer, constraint propagation, abstraction and refinement, change of basis: each lens makes some problems easy and others no easier. Running several lenses at once and letting them disagree is cheap insurance.

C4 · ECONOMICS

Cheap models are good enough at the leaves

If the leaves are small enough, a model costing about 1/50 as much as a frontier model solves them reliably. Intelligence then comes from the structure: search, verification, composition and selection.

Why it should work: local verification beats global retries

A toy model of claims C1 and C2. Three ways to spend about the same compute on a task that needs n correct steps:

  • Monolithic chain: one pass, success = pn.
  • Global best-of-k: sample k whole chains and assume a perfect final checker picks a correct one if any exists: 1 − (1 − pn)k.
  • Decomposed + local verifier: each step is retried up to k times until an imperfect verifier (recall r, specificity q) accepts it. A false accept lets an error through.
The key quantity is the verifier's false-accept rate (1 − q), not the solver's accuracy. Moving q from 0.9 to 0.99 matters more than moving p from 0.90 to 0.95. This shapes the whole design: we spend effort making pieces checkable (formal post-conditions, executable checks, cross-lens agreement) before making solvers smarter.

Decomposition lenses

A lens is a strategy that turns one problem into a graph of smaller problems plus a composition rule for joining their answers. Each lens borrows a structure from mathematics or engineering. The harness starts with a fixed library and later lets agents propose new lenses (phase 4).

Divide & conquer / FEM

Ω = ⋃ Ωᵢ, glue on shared boundaries

Split the state or space into regions that interact only through interfaces. Solve each region, then reconcile the boundary conditions.

Compose: boundary reconciliation

Series expansion

f ≈ f₀ + εf₁ + ε²f₂ + …

Solve a simplified core problem first, then add corrections for each relaxed constraint in order of importance until the residual is zero.

Compose: additive refinement

Abstraction / refinement (HTN)

plan at level L, refine to L−1

Make a coarse plan of macro-actions, then expand each one. This matches hierarchical task networks and is the main lens for planning benchmarks.

Compose: substitution

Constraint propagation

domains Dᵢ ← Dᵢ ∩ consistent(Cⱼ)

Extract the constraints explicitly and let cheap agents prune domains in parallel. This works best on puzzles like Zebra and Sudoku, and on scheduling.

Compose: intersection / arc-consistency

Dynamic programming

V(s) = opt over a of [ c(s,a) + V(s′) ]

Find overlapping subproblems, solve and memoize each once, and build answers bottom-up. Multi-digit arithmetic and sequence alignment fit here.

Compose: recurrence

Backward chaining

goal ⇐ subgoals ⇐ … ⇐ facts

Start from what must be true at the end and regress through preconditions. Multi-hop QA becomes a chain of single-hop lookups with checkable bridge entities.

Compose: proof tree

Change of basis

solve in T(x), map back with T⁻¹

Re-represent the problem as a graph, an equation system, code, a table or a known puzzle class, so that it becomes routine. For example, Mystery Blocksworld is Blocksworld under renaming.

Compose: inverse transform

Invariants & symmetry

find I with I(s) = I(s′) under all moves

Find quantities that must be preserved, or symmetries that collapse the search. These are cheap to check and often prove a problem unsolvable fast.

Compose: quotient / pruning

Sampling & bounding

upper/lower bounds, Monte Carlo

Estimate the answer roughly or bound it before solving it exactly. Bounds act as verifiers for other lenses' candidate answers.

Compose: bracket tightening

Architecture

The design is a blackboard system. Agents never call each other directly. They read from and write to a shared problem graph, and a scheduler decides which work is worth funding next. This loose coupling is what lets the system organize itself.

Design principles

  • Checkability first. A subproblem is only accepted onto the graph if it carries a verification contract: an executable check, a formal post-condition, or a "two independent lenses must agree" rule.
  • Verifiers outside the model where possible. Use PDDL validators (VAL), SAT/SMT solvers, Python execution and unit checks. This follows Kambhampati's LLM-Modulo idea: models generate, sound critics check.
  • Diversity is a resource. Use different model families, prompts and lenses, so that errors are less correlated and votes mean something.
  • Everything is a trace. Every node records who made it, at what cost, and how it was verified. Traces become training data later.

Cheap model pool (initial)

Use small, fast models from several families so errors decorrelate. Examples: Claude Haiku 4.5, Gemini Flash-class models, GPT mini-class models, and open-weight 7–32B models (Qwen, Llama, Mistral, DeepSeek distills) served locally through vLLM for near-zero marginal cost.

The ceiling reference is a frontier reasoning model run alone. The headline claim is matching or beating it at a fraction of the cost, or beating it at high complexity where it collapses.

The problem graph

The graph is the central data structure. Nodes are typed so that agents can find work by pattern-matching: for example, "a Subproblem with no accepted Candidate" or "two Candidates that Contradict."

How the swarm organizes itself

There is no central planner that scripts which agent does what. Order comes from four simple mechanisms, each a separate component that can be switched off for ablation.

1 · Stigmergy (pheromones on the graph)

Nodes carry signals: unsolved, contested, high-value, stale. Agents pick work by sampling nodes weighted by signal, like ants following trails. Contradictions emit strong signals that attract critics and re-splitters.

2 · A budget economy

Each lens is an arm in a multi-armed bandit (UCB or Thompson sampling) over the remaining token budget. Its reward is verified progress: accepted nodes weighted by how close they are to the goal. Lenses that stall lose funding.

3 · Adaptive granularity

When a leaf fails verification repeatedly, it is split further. When a subtree is solved easily, sibling subtrees are merged into bigger chunks. Each cheap model finds its own working size, much like adaptive mesh refinement in FEM.

4 · Evolution of lenses

Across problems, lens prompts and composition rules are mutated and recombined, and selected on (accuracy, cost). In phase 4, "lens inventor" agents propose new decompositions written as programs, which are kept only if they pay off on held-out problems.

Benchmarks: what we will measure and why

The selection rule: (1) a complexity knob that can be turned up until single models collapse, (2) an automatic sound verifier so results are not judged by an LLM, and (3) prior published results showing frontier models degrade, so that a win means something. Kambhampati's planning work is the backbone because it meets all three criteria and makes the strongest form of the "LLMs can't plan" claim.

Experimental design

Baselines (same budget where noted)

  • B0 Cheap model, direct answer
  • B1 Cheap model, chain-of-thought
  • B2 Cheap model, self-consistency (majority vote) at equal $ budget
  • B3 Tree-of-Thoughts / best-first search at equal $
  • B4 LLM-Modulo (generate, then external critics) as the closest prior architecture
  • B5 Frontier reasoning model alone, as the ceiling reference, with cost recorded

Metrics

  • Collapse point N₅₀: the complexity at which accuracy falls below 50%. This is the headline number.
  • Accuracy vs. complexity curve, not a single averaged score
  • $ per solved instance and tokens per solved instance
  • Obfuscation gap: Blocksworld minus Mystery Blocksworld (smaller means more real reasoning)
  • Verifier false-accept rate, measured against ground truth
  • Wall-clock time and number of agent calls

Game plan

The order is: measuring tools first, then baselines, then the smallest version of the idea, and only then self-organization. Each phase has an exit criterion so we know when to stop polishing.

Wk 1–2

Phase 0 · Eval harness

  • A single Task interface: generate(complexity, seed), verify(answer), render(prompt)
  • Vendor PlanBench (with VAL), Hanoi and the other puzzles, ACPBench, ZebraLogic, Faith & Fate tasks, Natural Plan
  • A model gateway with per-call cost accounting, caching, seeds and rate limits; open-weight models on vLLM
  • Results store with trace logging, and a dashboard that plots accuracy vs. complexity
Exit: one command runs any model × task × complexity sweep and plots the curve.
Wk 2–3

Phase 1 · Baselines and collapse curves

  • Run B0 to B3 for 3 or 4 cheap models and B5 for 1 frontier model across the core suite
  • Measure N₅₀ for each; fit pn-style curves to estimate effective per-step reliability
  • Reproduce the published shapes (e.g. Mystery Blocksworld gap, Hanoi collapse) as a sanity check
Exit: a reproduced baseline table and curves, so we know the target.
Wk 3–6

Phase 2 · Fixed-lens decomposition (minimum version)

  • Problem graph and blackboard; three hand-built lenses: HTN, constraint propagation, change of basis
  • Solver and verifier roles; verifiers use tools (VAL, a Python simulator) where available
  • Static schedule: try lenses in order, retry leaves k times
Exit: H1 and H2 hold on Blocksworld and Faith & Fate (clear shift of N₅₀ at equal $).
Wk 6–10

Phase 3 · Self-organizing swarm

  • Stigmergic work selection, a bandit budget economy, adaptive split and merge
  • A heterogeneous model pool, with cross-lens agreement used as a verifier
  • Full ablation grid for H3 and H4; extend to Natural Plan, TravelPlanner, ZebraLogic and MuSiQue
Exit: H3 and H4 hold on at least 3 of 5 core benchmarks; H5 holds on at least 1.
Wk 10+

Phase 4 · Lens invention and stretch goals

  • Lens-inventor agents write new decompositions as programs; an evolutionary loop over the lens library
  • Attack ARC-AGI-2 and AIME, and a SWE-bench subset
  • Distill: train a small model on harness traces to see if the structure can be internalized
Exit: an invented lens beats every hand-made lens on some held-out task family.

Risks and open questions

Correlated errors

If every cheap model makes the same mistake, voting and retries don't help. Mitigation: mix model families, use tool verifiers, and measure error correlation directly.

The formalization bottleneck

Turning natural-language problems into checkable pieces is itself a hard reasoning step, and a single wrong constraint corrupts everything downstream. Mitigation: formalize redundantly, then check that the formalization reproduces the problem's stated facts.

Composition can lose information

Some problems aren't decomposable: the pieces interact everywhere, like a chaotic system. We need a test for "this problem isn't decomposable," and should fall back to search there.

Cost blow-up

Swarms can burn tokens. Every result is reported at equal $ budget, and the economy has to earn its overhead.

Benchmark validity

The rebuttals to the Hanoi paper showed how output-length limits and unsolvable instances can fake a "collapse." Mitigation: use compact answer formats, filter for solvable instances, and report the token budget for every point.

Is it reasoning or a planner with extra steps?

If the winning lens is "translate to PDDL and call a solver," that is a valid result (LLM-Modulo), but it's a different claim. Report results both with and without external solvers.
